# MCP tools (real Playwright MCP + real LLM)

This page proves xgraph's central architectural claim with a real,
independently-sourced tool provider: **[Model Context
Protocol](https://modelcontextprotocol.io/)** tools, served by a real
[Playwright MCP](https://github.com/microsoft/playwright-mcp) server, bound
to a real LLM agent, with **zero MCP-specific code anywhere in xgraph**.

Source: [`examples/mcp_playwright_tool_agent.py`](https://github.com/samamuniharish/langgraph-xai/blob/main/examples/mcp_playwright_tool_agent.py).

## What actually runs

1. A real Playwright MCP server is launched over stdio:
   `npx -y @playwright/mcp@latest --headless --isolated`.
2. Its (real, 26-tool) tool set is loaded via
   `langchain_mcp_adapters.MultiServerMCPClient` — an independent,
   general-purpose LangChain/MCP integration, not anything xgraph ships.
3. A real `langchain.agents.create_agent` agent is built against a real
   `ChatOpenAI` model (`gpt-5.6-luna`).
4. The compiled agent graph is instrumented with **one line**:
   `runtime.instrument(agent)`.
5. The agent is invoked on a real browsing task.

```python
async with MultiServerMCPClient(
    {
        "playwright": {
            "command": "npx",
            "args": ["-y", "@playwright/mcp@latest", "--headless", "--isolated"],
            "transport": "stdio",
        }
    }
) as client:
    tools = await client.get_tools()
    agent = create_agent(model=model, tools=tools)
    runtime = XAIRuntime(graph_id="mcp-playwright-agent")
    instrumented = runtime.instrument(agent)
    result = await instrumented.ainvoke({"messages": [...]})
```

```bash
uv run --system-certs python examples/mcp_playwright_tool_agent.py
```

## Real captured output

10 canonical records were captured for one real run, all sharing one
`run_id`/`trace_id`:

```text
Execution
execution.started
tool.execution        <- browser_navigate
state.transition
tool.execution        <- browser_snapshot
state.transition
state.transition
state.transition
state.transition
execution.completed
```

Every `tool.execution` record carries the real MCP tool name
(`browser_navigate`, `browser_snapshot`), a real `latency_ms`, and a
`tool_call_id` generated by the agent framework — with no MCP-aware code
inside `langgraph_xai.instrumentation` or `langgraph_xai.runtime` at all. The
same generic LangChain callback surface (`on_tool_start`/`on_tool_end`) that
captures a plain Python `@tool` also captures an MCP tool, because from
LangChain's perspective they are both ordinary `BaseTool` invocations.

## Why this matters

This is the practical proof of
[ADR-011](../architecture/decisions.md#adr-011-the-runtime-orchestrates-provider-neutral-capability-interfaces):
adding support for a brand-new tool ecosystem (MCP, released after most of
xgraph's design) required **no code change** in xgraph — only in the
application wiring the tools into LangChain, which is exactly where that
responsibility belongs.
